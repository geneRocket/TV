# 弹幕重复加载与通知排查（2026-10-25）

用户反馈：正常开始播放时，反复出现“弹幕加载成功”通知，怀疑视频或弹幕被重复启动。

## 已确认的问题

应用源码、内置弹幕库没有此固定提示。在设备缓存的接口 JAR 中找到 `com.github.catvod.spider.Danmu`：AppDanmu、Danmu、DiyDanmu 等代理读取弹幕成功后会通知“弹幕加载成功”。这是请求的副作用，每次重复请求都可能再次通知。

TV `onResume → reconcilePlaybackUiState → refreshDanmaku → prepareDanmaku` 会重新下载并准备弹幕，没有区分“同一集同一来源正在加载/已经加载”和“确实需要换来源或换集”。原有 requestId 只丢弃迟到的回调，不能阻止请求发出或接口 JAR 先弹通知。新增的弹幕进度采样只同步时钟，不调用下载或视频解析。

原生受控复现中，先播放一个本地视频并加载弹幕，再主动调用三次界面恢复逻辑，弹幕 XML 收到 4 次请求，断言失败。这三次调用是测试主动触发，不代表用户进行了三次操作，也不是在第三方接口上抓到的启动时请求日志。复现针对已确认的重复下载路径；不能据此断言用户实际环境中所有重复通知都由这一条路径引起。

## 修复

引入主线程使用的 DanmakuLoadGate，以播放请求代次和弹幕来源确定归属。同一请求、同一来源只启动一次加载，保留原任务的回调归属，界面恢复只同步可见性和播放状态。新播放代次即使使用同一个代理 URL，也会重新读取弹幕，避免跨集复用动态代理内容。

换源、清空/禁用、手动重新选取以及异常失败会释放相应归属；迟到的旧成功或失败不能覆盖当前任务。手动选择相同来源仍能主动重试。没有改动全局 Toast 行为或接口 JAR，也没有屏蔽通知来掩盖重复请求。

## 验证

- 6 项新增单测：重复准备、同地址新播放代次、切源与旧回调、失败重试、主动失效和清空来源。
- TV 原生受控测试修复前：同一个播放请求，初始化加三次界面恢复共请求弹幕 4 次，断言失败。
- 修复后 TV 与 Mobile 隔离包均通过：初始化加三次恢复只请求 1 次，播放请求代次保持不变；打开第二个视频使用相同弹幕地址，总计 2 次；手动重新选择同一来源，总计 3 次。
- Native 测试使用 API34 Google APIs 临时只读模拟器 emulator-5556、90 秒本地视频与带延迟的弹幕 XML。实测是 HTTP 请求数与真实页面加载状态；没有执行第三方 JAR 的通知分支，也不能替代实体设备上原接口的弹窗验收。
- 两端 Java arm64 单测通过：TV 951、Mobile 924；失败、错误、跳过均为 0。两端 Debug 普通构建成功。Lint 无错误，TV 179、Mobile 291 条警告。
- 普通 APK 不含 RefactorReceiver；脚本语法及差异空白检查通过。未修改视频启动、重试和自动切源策略，未改动数据库、预置二进制或运行时依赖。

设备现有包仅用于读取相关缓存进行排查；原生测试安装在新模拟器的独立测试包。现有 emulator-5554 未安装或启动测试包。原接口在实体设备上的启动通知频次仍需实际验证。
